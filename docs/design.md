# 设计说明

## 背景

训练场景希望减少补给站配送批次的重复核对，提高服务可追溯性。现已归档[六角色、36 条演练事实](discovery/README.md)，并整理了[候选需求及证据映射](requirements.md)。这属于合成演练，尚未确认真实业务需求或通过验收。

## 当前代码：早期流程演示

采用 Python 标准库，将命令行、核心业务与通用校验分离。需求记录不可变，业务函数返回新记录，由调用方保存。

```text
待调度 → 指定配送人员 → 已派单 → 指定签收人员 → 已签收
```

记录包含站点、物资、正整数数量、状态、配送人员和签收人员。演示采用单物资、全量签收，数量单位在物资名称中注明。

该演示早于本次访谈归档，只操作本地内存对象，不接入外部系统。报告 f32 限定试点只读、无执行接口，因此现有派单/签收函数不作为真实集成能力，也不表示满足报告的需求。

## 根据报告建议的下一版设计（未实现）

```text
脱敏只读样本 → 原行与快照留存 → 关键字段/关联/单位/版本核对
                                      ↓
                           一页缺项清单与来源位置
                                      ↓
                            人工复核与确认链记录
```

数据候选字段来自 f31/f34：站点编号、物资种类、单位、批次、签收时间、业务发生时间与系统接收时间。原行定位、版本有效期、确认状态、责任人和未结项来自 f23–f25/f33/f42。字段格式、关联键和具体规则仍需确认，不能从描述推造换算率或过期阈值。

只读核对需区分缺失值与未确认值（f31）；异常保留原行（f33）；读取失败保留有时间标记的上次快照（f35）；无法确认时转人工（f44）。不自动写回、发消息或调用业务执行接口（f32）。上述能力均尚未实现。

## 当前边界

没有数据库、网页、登录鉴权、库存扣减、部分签收、取消、配送批次编号、版本核对或审计日志。人员字段仅用于演示，不构成权限控制。

## 仍需确认

具体批次与确认人、关联键、换算依据、过期阈值、升级路径、数据留存规则等，见[需求分析中的待确认问题](requirements.md#待确认问题)。仍需取得样本文件和书面 Brief；报告中的虚构基线不作为实验结果。

后续顺序：确认待决项及最小范围 → 获取虚构样本和明确规则 → 实现只读核对原型 → 验证来源、单位、版本和人工复核 → 按约定样本开展验收。
