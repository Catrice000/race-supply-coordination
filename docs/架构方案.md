# 赛事补给协同助手技术架构方案

更新日期：2026年10月30日。状态：推荐架构，供需求确认与后续实施使用；本文不代表相关功能已经开发完成。

## 1 项目定位与范围

系统服务赛事运营企业的普通员工和管理员。员工只使用聊天页，在授权赛事和站点范围内上传资料、查询补给记录、查看差异和来源；管理员负责赛事与资料维护、知识发布、规则维护、图谱查看以及对话和处理记录查询。

本项目继续使用赛事补给业务，不引入示例中的报销制度、发票、报销单或财务审批。

现状业务主线为：站点需求 → 库存核对 → 装车 → 签收 → 余料回收。首期建设资料查询与核对辅助能力，不自动派单、不修改外部库存、不代替食品安全、医疗补给或应急调度判断。访谈资料为合成演练，具体业务规则仍需确认。

### 已确定约束

- Python 异步 FastAPI 后端。
- 大模型通过 API 调用，首个适配 OpenRouter，可替换供应商。
- 知识库必须支持向量化检索，并以知识图谱展示实体和关系。
- 两个系统角色：employee、admin；不另外增加第三个角色。
- 目前没有 OpenRouter 密钥，先建设适配代码与模拟测试；真实调用待密钥配置后验证。

### 本方案建议但尚需确认

- 首期单企业、多赛事，按赛事和站点授权，不建设对外多租户 SaaS。
- 管理员拥有资料发布与核对事项确认权限；若需要业务人员确认，可通过管理员中的独立权限项授权，不使全部管理员自动具备所有业务决定权。
- 员工可补充说明、生成补给需求草稿，但草稿不等于下达配送指令。
- 图谱独立管理页面只放在管理员后台；员工聊天内可按权限展示局部关系卡片或来源链，避免增加员工端独立页面。

## 2 架构选型结论

推荐：**模块化单体 FastAPI + PostgreSQL/pgvector + 文档 RAG + 有来源的知识图谱 + 独立后台任务进程**。

| 部件 | 推荐方案 | 原因 |
| --- | --- | --- |
| 员工端 | Vue 3聊天页 | 支持附件、流式回答、来源引用及结构化结果卡片 |
| 管理员端 | Vue 3管理界面 | 维护赛事、资料、规则、图谱和记录；与员工端共用后端 |
| API服务 | FastAPI、Pydantic、SQLAlchemy异步会话 | 分离接口、业务、模型适配及数据访问 |
| 关系与向量数据 | PostgreSQL + pgvector | 同一数据库管理权限、版本、业务记录、文本块与向量 |
| 原始文件 | 本地受控目录起步，预留S3兼容对象存储接口 | 原文件不放公共静态目录；下载必须鉴权 |
| 文档处理 | 数据库任务表 + 独立worker | 长耗时解析、嵌入和抽取不阻塞聊天请求；首期无需引入多套队列服务 |
| 图谱存储 | PostgreSQL实体表、关系表及证据表 | 首期只需局部关系查询和可视化，不额外部署图数据库 |
| 模型服务 | ChatProvider与EmbeddingProvider分别抽象 | 对话模型与向量模型分别配置，不能假定同一个模型同时支持两者 |
| 部署 | 单服务器容器部署，TLS反向代理 | 首期运行web、api、worker和数据库；保留备份与升级方式 |

FastAPI的异步处理主要解决数据库和网络I/O并发；同步解析库、CPU密集型解析不直接放入异步请求处理器。较长任务交由worker执行。依据：[FastAPI并发说明](https://fastapi.tiangolo.com/async/)。

## 3 RAG 与 LLM Wiki 的判断

这里的 LLM Wiki 指把原始资料编译成互相链接的知识页面、持续整理和维护的方式，不是一个固定的数据库或统一标准产品。参考：[LLM Wiki原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。

| 比较项 | 文档RAG | LLM Wiki |
| --- | --- | --- |
| 知识依据 | 查询时检索原始资料片段 | 查询经模型整理的知识页面，并追溯原始来源 |
| 更新处理 | 发布新版本并重建相关片段/向量 | 需同步更新受影响页面、链接和派生结论 |
| 本项目适用点 | 需要回答具体站点、批次、版本和来源问题 | 适合整理术语解释、跨文档FAQ和操作知识 |
| 主要关注 | 检索漏召回、资料权限、版本与引用 | 编译遗漏、派生错误及旧知识未同步失效 |
| 推荐位置 | 首期问答主链路 | 第二阶段作为经过审核的派生知识层 |

**推荐先用RAG，保留Wiki扩展位置。** 本项目中的数量、单位、签收时间、版本和确认状态应有原始依据，不能只依赖模型总结页面。Wiki页面即使增加，也必须标记为派生内容，保留来源和审核状态，并服从原始资料的版本与权限。

**向量检索、知识图谱展示与GraphRAG是三件事。** 首期同时做向量检索和图谱展示，但不直接部署全量GraphRAG。后续只有在跨实体、多跳问题的验证集上证明图谱扩展检索有收益，再加入受控的一至两跳检索。GraphRAG项目参考：[Microsoft GraphRAG](https://github.com/microsoft/graphrag)。

### 首期检索链路

身份与赛事授权 → 结合问题确定赛事、站点、批次及查询时间 → 在可见且适用的已发布资料中检索 → 向量与关键词候选合并 → 相关片段重排 → 引用来源 → 模型解释 → 校验引用及权限 → 返回回答。

精确数量、待签收记录和统计查询走结构化业务查询；语义说明走RAG；单位换算和差异判定走确定性规则。模型不自行执行任意SQL，也不凭向量近似结果计算库存。

向量模型的供应商、模型ID、维度与版本必须记录。更换向量模型时重建索引，不混用不同模型产生的向量。小数据集先采用带权限过滤的精确相似度检索，规模扩大后再评估HNSW；近似索引与过滤组合需测召回，不能把过滤后少结果误认为无资料。参考：[pgvector官方文档](https://github.com/pgvector/pgvector)。

## 4 四层架构图

```text
┌────────────────────── 入口层 ──────────────────────┐
│ 普通员工：聊天、上传、查询、来源查看、补充说明           │
│ 管理员：赛事/授权、资料、规则、图谱、记录、任务状态       │
│ HTTPS；聊天采用SSE事件流；上传与任务查询采用HTTP接口      │
└────────────────────────┬─────────────────────────┘
                         ↓
┌────────────────────── 服务层 ──────────────────────┐
│ FastAPI：登录鉴权、角色/赛事/站点权限、参数与文件校验      │
│ 会话服务、文件服务、知识发布、批次查询、草稿与核对服务      │
│ 限流/额度、审计、任务提交、错误处理及流式响应生命周期      │
└────────────────────────┬─────────────────────────┘
                         ↓
┌────────────────── 智能体编排层 ────────────────────┐
│ 意图识别 → 工具选择 → 权限限定的数据查询/RAG             │
│ 确定性核对 → 可选图谱查询 → 模型组织回答 → 引用校验        │
│ ChatProvider / EmbeddingProvider；首接OpenRouter        │
│ 超时、拒答、缺依据转人工；工具白名单；无自动业务审批       │
│ worker：解析、分块、向量化、实体关系抽取、审核待发布       │
└────────────────────────┬─────────────────────────┘
                         ↓
┌──────────────────── 数据模型层 ────────────────────┐
│ PostgreSQL：用户、权限、会话、消息、资料版本、业务明细     │
│ pgvector：文本块向量；图谱：实体/关系/证据               │
│ 任务表、核对结果、确认记录、审计与模型调用记录            │
│ 文件存储：原件、解析产物；派生数据可按版本失效和重建       │
└───────────────────────────────────────────────────┘
```

智能体编排采用可测试的固定工作流和工具路由，首期不做多个自主智能体相互调用。业务服务拥有权限和事务边界，模型只提供建议或工具参数，不能绕过服务层直写数据库。

流式输出先发送检索/处理进度，完整答案的引用与可见范围校验后再发送正式回答，避免把未经验证的正文先推给员工。断线和取消应记录状态，不能把半段回答保存成已完成消息。

## 5 知识图谱设计

### 5.1 展示对象

```text
赛事 ─包含→ 站点
赛事 ─包含→ 配送批次
配送批次 ─供应→ 站点
需求明细 ─申请→ 物资
出库明细 ─履行→ 需求明细
签收明细 ─对应→ 出库明细
物资 ─使用→ 单位换算规则
规则/关系 ─依据→ 文档版本中的片段或原始业务行
```

配送批次编号与物资生产批号分别建模。部分配送、分次签收采用独立明细和显式关联，不默认用“站点+物资”作为唯一键。

### 5.2 建设与发布

优先从已核对的结构化数据生成关系；非结构化材料可让LLM提出实体与关系候选。候选进入管理员审核，不把模型抽取的高置信度等同于真实或已确认。

节点和关系都保留来源版本、业务有效期、审核状态和关联业务主键。每条图谱关系至少有一项证据，点击关系能够回到文件页码、文本块或表格行。撤回文档后，相关派生关系退出可见查询，不删除历史审计。

图谱后台采用Cytoscape.js或同类组件，提供赛事、站点、批次过滤和局部展开。默认不加载整库。员工看到的局部图谱沿用与问答相同的权限，不泄露隐藏节点名称和关系数量。

## 7 数据库表设计

### 7.1 通用约定

主键采用UUID，时间使用带时区时间戳；金额/数量如需精确计算使用numeric，不使用浮点数。系统仅定义employee/admin两个角色，通过显式授权控制赛事、站点及管理员操作。密码仅保存安全哈希；模型密钥不进入普通业务表或聊天记录。

系统记录时间与业务发生时间分离。原始业务资料不可被模型改写。表格明细必须能定位原文件、工作表及原始行。

### 7.2 用户 会话 消息

| 表 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| users | id, login_name, password_hash, display_name, role, is_active, created_at | login_name唯一；role仅employee/admin；停用后拒绝新请求 |
| user_event_grants | id, user_id, event_id, station_id, permission | 用户与赛事/站点授权；station_id为空表示显式赛事级授权；避免NULL导致重复授权 |
| conversations | id, user_id, event_id, title, status, created_at, updated_at | 普通员工只访问本人会话；赛事可切换时需重建检索上下文 |
| messages | id, conversation_id, sequence_no, role, content, status, request_id, provider, model, created_at | 会话内sequence_no唯一；记录pending/completed/failed/cancelled等状态 |
| message_citations | id, message_id, document_version_id, chunk_id, source_record_id, quote_text | 至少指向一类真实证据；下载引用时重新检查可见权限 |
| message_attachments | message_id, file_id | 记录消息与文件关系；不能只靠文件名定位 |

### 7.3 赛事 资料与向量库

| 表 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| events | id, name, starts_at, ends_at, status | 赛事主档 |
| stations | id, event_id, station_code, name | 同一赛事station_code唯一 |
| delivery_batches | id, event_id, batch_code, business_date, status | 同一赛事batch_code唯一；与物资生产批号不同 |
| files | id, uploaded_by, event_id, object_key, sha256, media_type, size_bytes, scan_status | 存储引用及完整性；文件访问按关联资料与授权校验 |
| knowledge_documents | id, event_id, title, document_type, owner_id, status | 报销制度文档替换为赛事规程、补给规范、交接说明等逻辑文档 |
| document_versions | id, document_id, version_no, file_id, effective_from, effective_to, status, published_by, published_at | document_id+version_no唯一；上传与发布分离，发布需解析/向量/审核均完成 |
| document_chunks | id, version_id, chunk_no, text, page_no, sheet_name, row_start, row_end | version_id+chunk_no唯一；保留引用定位 |
| chunk_embeddings | id, chunk_id, embedding_model_id, embedding_version, embedding, status | chunk+模型版本唯一；维度与指定模型一致，不混用模型索引 |
| ingestion_jobs | id, version_id, job_type, status, attempt_count, lease_until, error_code, created_at | 持久化任务、幂等重试、worker失效恢复；失败版本不发布 |

发布状态建议为uploaded→processing→pending_review→published，另有failed/withdrawn。不要把文档版本号最大的文件自动当成业务有效版本；检索按查询业务时间、有效期、发布状态和访问范围筛选。历史问题可使用历史有效资料，引用中注明版本。

### 7.4 补给业务与草稿

| 表 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| materials | id, code, name, specification, base_unit | 区分规格，避免所有物资共用箱/份换算 |
| supply_records | id, event_id, station_id, delivery_batch_id, record_type, material_id, quantity, unit, occurred_at, received_at, source_version_id, sheet_name, source_row | record_type区分需求/出库/签收/回收；原始行只读保存 |
| supply_record_links | id, from_record_id, to_record_id, linked_quantity, unit, status, confirmed_by | 需求到出库、出库到签收的显式关联；支持分次处理与人工确认 |
| conversion_rules | id, material_id, from_unit, to_unit, factor, effective_from, effective_to, source_chunk_id, rule_version, status | factor大于0；同规格同单位同适用范围不能发布冲突有效规则 |
| supply_request_drafts | id, owner_id, event_id, station_id, delivery_batch_id, conversation_id, status, revision, created_at, updated_at | 对应示例中的报销单草稿；本项目为补给需求草稿，不是执行单据 |
| supply_request_draft_items | id, draft_id, material_id, quantity, unit, reason, source_message_id | 草稿明细结构化保存；正数数量校验；生成后须人工确认 |
| reconciliation_runs | id, event_id, delivery_batch_id, input_version_set, rule_version_set, status, created_by, started_at, completed_at | 固定一次核对所使用的输入和规则版本 |
| reconciliation_issues | id, run_id, issue_type, source_record_id, related_record_id, details, status | 区分数量差异、缺依据、关联冲突与未确认；不把未知当通过 |
| review_actions | id, issue_id, actor_id, action, comment, input_revision, created_at | 追加式复核历史；数据变化需重新复核，保留旧确认依据 |

草稿状态首期只做draft/confirmed/cancelled。confirmed表示用户确认草稿内容，不等于业务审批通过或已执行出库；后续真实提交、调度及库存写入需单独授权设计。

### 7.5 图谱与审计

| 表 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| graph_entities | id, event_id, entity_type, business_ref_id, canonical_key, label, status | 同类型规范键唯一；别名独立管理或保存在受校验结构中 |
| graph_relations | id, event_id, source_entity_id, relation_type, target_entity_id, valid_from, valid_to, status, reviewed_by | 只显示有证据、已审核且当前适用的关系 |
| graph_evidence | id, relation_id, chunk_id, source_record_id, extraction_method, confidence | 每条已发布关系至少一项来源；不能只记录模型置信度 |
| audit_logs | id, actor_id, action, target_type, target_id, request_id, created_at, metadata | 管理员查看员工记录、下载资料、发布及确认均留痕；敏感字段最小化 |
| model_calls | id, request_id, provider, model, purpose, status, input_tokens, output_tokens, latency_ms, error_code, created_at | 区分chat/embedding/extraction；不记录密钥或完整敏感提示词 |

数据库外键需约束站点、批次和资料属于一致赛事。应用账号采用最小权限；若启用PostgreSQL行级安全，注意表所有者等角色可能绕过策略，不能仅配置策略就认为隔离完成。参考：[PostgreSQL行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。

## 8 权限与数据发布

员工可上传资料到个人待处理区，但上传不等于进入全员知识库。只有管理员审核发布后，资料才进入对应授权范围的共享检索。员工个人附件只在本人授权会话中使用；管理员调阅须有相应权限并留痕。

检索、结构化查询、图谱、来源预览、文件下载、导出都在服务端执行同一授权规则。不得先检索全库再让LLM自行决定哪些内容可展示。会话历史也不能被当成跨用户共享知识。

文件内容属于不可信资料，不能覆盖系统规则或要求模型执行指令。首期工具白名单包括授权业务查询、资料检索、规则核对和草稿生成；正式确认由人触发服务端接口。

## 9 第一周最小验证目标

**一周内完成：管理员发布一份赛事补给说明和一组脱敏样例，员工在聊天页提出问题，系统返回有正确引用的回答；管理员能看到对话记录和带来源的局部图谱。**

| 时间 | 实施内容 | 可检查结果 |
| --- | --- | --- |
| 第1天 | 项目骨架、数据库迁移、两个角色与两个员工测试账号 | 员工A无法读取员工B会话；员工无法访问管理员接口 |
| 第2天 | 文件上传、文本PDF/CSV解析、任务状态与版本管理 | 原件可追溯，解析失败可见；未发布内容不进入共享问答 |
| 第3天 | 接入一个向量模型、分块与带权限检索 | 同义提问能检索到适用片段；记录向量模型版本 |
| 第4天 | 完成OpenRouter对话适配、RAG回答及引用检查 | 有依据时回答并附来源；无依据时明确说明；错误和超时不伪装成功 |
| 第5天 | 从样例生成实体关系并由管理员发布，完成界面与用例验证 | 图谱点击关系能查看来源；与当前授权和文档版本一致 |

### 最小验收用例

1. 管理员导入一份补给说明与需求/出库样例，查看解析任务，审核发布。
2. 员工查询某站点某批次的补给要求，回答带有效文档引用。
3. 员工查询具体数量，由结构化查询返回，不用LLM猜数。
4. 缺少单位换算依据时返回待确认，不计算虚假的差额。
5. A、B员工及未授权赛事资料的隔离用例全部通过。
6. 管理员查看赛事→站点→批次→物资的局部图谱，关系有来源；未审核关系不可见。
7. 文档撤回或权限取消后，问答、图谱和来源下载均不再提供对应资料。
8. 模型调用失败时保留问题和失败状态，支持人工重试，不静默切到付费更高或不同数据政策的供应商。

没有密钥时，可以用模拟适配器验证流程与错误处理，但不能宣称真实LLM接入或向量检索效果已验收。真实闭环至少需要一个对话模型和一个向量模型的可用API或另行批准的本地向量模型。

第一周不追求完整60条业务验收、所有格式、复杂审批、完整图数据库、LLM Wiki自动维护或实时外部系统同步。60条样本属于后续约定范围的验收，不以第一周演示替代。

## 10 待决策事项

- 是否接受首期单企业及管理员后台中的业务确认权限划分。
- 员工附件是否只供本人会话使用，哪些资料需要申请共享发布。
- 可发送给OpenRouter及下游供应商的数据范围、预算和供应商限制。
- 对话与向量模型选择；目前不指定尚未验证可用的模型ID或价格。
- 单服务器部署位置、真实并发目标、资料及日志保留期限。
- 关联编号、换算规则、版本有效性和部分签收规则的业务确认人。

这些事项影响权限、索引、留存及真实调用，需在相应开发阶段前确认；本文不替代客户对业务规则和数据授权的决定。
